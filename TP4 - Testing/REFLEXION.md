# REFLEXION.md - TP4 Testing

### 1. ¿Cuántos tests unitarios, de integración y E2E tenés? ¿Por qué esa proporción?
En nuestra suite contamos con 15 tests unitarios en `test_checkout.py`, 4 tests de integración en `test_integracion.py` y 4 tests E2E en `test_e2e.py`. Esta proporción sigue estrictamente los principios de la pirámide de automatización de pruebas de software. La base es predominantemente unitaria porque estas pruebas se ejecutan en milisegundos de forma aislada para validar reglas lógicas puras como las de `checkout.py`. Las pruebas de integración son menores en cantidad y evalúan el comportamiento directo contra una base SQLite real mediante `pedidos.py`. Finalmente, los tests E2E constituyen el grupo más reducido debido a que simular el ciclo HTTP completo es más lento.

### 2. ¿Qué falla de pedidos.py no podía encontrarse con un test unitario de checkout.py? ¿Por qué?
Una falla de `pedidos.py` imposible de detectar en `checkout.py` fue la falta de implementación de la función de listado. Los tests unitarios de `checkout.py` solamente prueban funciones de cálculo en memoria sin interactuar con bases de datos ni con la API del módulo de persistencia. Al no ejecutar el módulo `pedidos.py` conectado a la base SQLite real, las funciones puras jamás pueden notar la ausencia de un método en la capa de datos. Este problema solo se expone al invocar la interfaz real del módulo dentro de la suite de integración en `test_integracion.py`. Por esta razón, el aislamiento de las pruebas unitarias es inadecuado para validar contratos de persistencia.

### 3. ¿Qué falla de api.py estaba en el paso de información entre dos partes del sistema? ¿Qué parte tendría que haberla resuelto?
Entre la API y el dominio ocurrió una falla al serializar los valores monetarios de tipo `Decimal` retornados por el checkout hacia formatos no precisos o cadenas al construir la respuesta JSON. Este desacople de tipos de datos afectó directamente la transmisión de información en el límite de la capa HTTP en `api.py`. La responsabilidad de resolver esta discrepancia correspondía a `api.py`, dado que la capa de controladores es la encargada de traducir los tipos de datos internos del dominio al protocolo de transporte HTTP. La solución requería formatear o castear explícitamente los campos antes de retornar el payload en el endpoint. Al omitir esta conversión en la frontera, la API expuso representaciones numéricas ambiguas al cliente.

### 4. ¿Cuál de las fallas que encontraste habría sido la más cara de descubrir en producción? ¿Por qué?
La falla más costosa de descubrir en producción habría sido el comportamiento detectado en `test_r10_4_rollback_transaccional_ante_error`, donde `guardar_pedido` omitió validar la cantidad cero y persistió registros inválidos sin hacer rollback. Si un cliente en un entorno real logra procesar un pedido con ítems de cantidad nula o precios corruptos, se generan inconsistencias financieras en la base de datos de la empresa. Las discrepancias monetarias derivan en cancelaciones con pasarelas de pago, reclamos de facturación y disputas contables complejas. Además, reparar transacciones corruptas requiere ejecutar scripts de migración riesgosos en la base de datos de producción y afecta gravemente la reputación del comercio. Encontrar esta falencia mediante la falla esperada del test evitó pérdidas económicas directas.

### 5. ¿Qué mide la cobertura, qué mide la mutación y qué mide la inyección de fallas? ¿En qué se diferencian?
La cobertura de código mide el porcentaje de líneas, sentencias o ramas ejecutadas por al menos una prueba durante la corrida de la suite. El testing de mutación modifica el código fuente de forma automática con pequeños cambios sintácticos para evaluar si las aserciones de los tests son capaces de detectar los cambios y fallar. La inyección de fallas, por otro lado, introduce deliberadamente errores de infraestructura o latencia para medir la tolerancia a fallos y la resiliencia del sistema. La diferencia fundamental radica en que la cobertura solo valida qué líneas fueron tocadas sin medir la efectividad de las aserciones. En cambio, la mutación mide la calidad real de los tests y la inyección de fallas mide la capacidad de recuperación del sistema ante situaciones imprevistas.

### 6. Si una IA escribiera tus tests de integración y E2E, ¿qué le faltaría probar? ¿Cómo lo comprobarías?
A una IA le faltaría probar casos de borde no documentados en la especificación, arrays conditions concurrentes en SQLite y comportamientos bajo fallas intermitentes de red. Para comprobar la suficiencia de los tests generados por la IA, ejecutaría pruebas de mutación sobre la capa de integración y realizaria fallos simulados durante las peticiones HTTP de los tests E2E. Asimismo, realizaría una revisión manual del reporte de cobertura de ramas para detectar combinaciones no contempladas. De esta manera garantizaría que los tests no sean meramente superficiales y protejan el sistema en producción.
